# 1.单例模式

单例模式（Singleton Pattern）是一种创建型设计模式，它确保一个类仅有一个实例，并提供一个全局访问点来获取该实例。这种模式在很多情况下都非常有用，尤其是在那些需要一个对象来协调动作并确 保对象一致性的场景中。

在一个项目中，全局范围内，某个类的实例有且只有一个。通过这个唯一实例向其他模块提供数据的全局访问，这种模式就叫单例模式。单例模式的典型应用就是：**任务队列**

- **单例模式的核心职责**：保证一个类仅有一个实例，并提供一个全局访问点。它**本身并不自动处理对实例内部数据的并发访问同步**。

1. ==**全局唯一实例**==：无论尝试多少次实例化这个类，它都只会返回一个对象实例。
2. **==减少资源消耗==**：当一个类只需要一个对象实例时，使用单例模式可以避免创建多个对象，从而减少 资源消耗。

# 1.1实现思路

1. 确保用户无法自己创建对象(构造函数私有化,删除拷贝构造函数）
2. 让类自己负责管理这唯一的一个对象(使用静态成员变量)
3. - 普通的成员属于对象,而静态成员变量不属于对象。
   - **静态成员变量**不能在构造函数中定义和初始化,需要在类的外部单独定义和初始化。
   - 静态成员变量和全局变量一样存放在全局区,可以把静态成员变量理解成是被限制在类中去使 用的全局变量。
4. 提供一个安全的全局访问点,即提供一个公开的接口,让用户可以使用这唯一的一个实例（静态成员 函数）
5. - 静态成员函数没有this指针,没有const属性，但是可以重载（静态与非静态成员函数名字相同 且参数相同不构成重载）
   - 访问方式:
     - 类名::静态成员函数(实参表);//推荐 
     - 对象名.静态成员函数(实参表);//和上面方法本质一样
   - 在静态成员函数中只能访问静态成员,不能访问普通成员,在普通的成员函数中,既可以访问静态 的成员也可以访问普通的成员。

不同的语言,不同的程序员,可能有多种实现方式,总体上可以分为两种:饿汉式和懒汉式

## 1.1.1 ==饿汉式==

- **在多线程模式访问单例对象是安全的，不一定整个程序就是安全的**

饿汉式单例模式(预先创建):（无论用或不用,程序启动即创建）

- 唯一的实例在类加载的时候创建,预先初始化(不管有没有用到,都创建这个实例) 
- 在类加载的时候创建,调用的时候反应速度快
-  在类加载的时候创建,有可能永远也用不到这个实例(资源浪费)

````c++
// 饿汉式
#include <iostream>
using namespace std;
class Singleton
{
// 1>私有化构造函数
private:
    //Singleton(int data):m_data(data) = defalut;
    Singleton(int data):m_data(data)
    {
        cout<<"创建单例对象"<<endl;
    }
// 删除拷贝构造函数和赋值运算符
    Singleton(const Singleton&) = delete;
  	Singleton& operator=(const Singleton&) = delete;
// 2>通过静态成员变量来维护唯一的对象
    static Singleton s_instance;
    int m_data;

public:
// 3>通过静态成员函数获取单例对象
    static Singleton& getInstance()
    {
        return s_instance;
    }
    void print(void)
    {
        cout<<m_data<<endl;
    }
};
Singleton Singleton::s_instance(123); // 需要提供一个初始值
int main()
{   cout<<"main函数开始执行"<<endl;
    Singleton& s1 = Singleton::getInstance();
    Singleton& s2 = Singleton::getInstance();
    cout << "&s1 = " << &s1 << endl;
    cout << "&s2 = " << &s2 << endl;
    s1.print();
    s2.print();

    return 0;
}
````

## 注意事项

### static Singleton s_instance是对象也是变量

在 C++ 中，`static Singleton s_instance;` 这一行声明的是一个 **静态成员变量（static member variable）**，但它本质上是一个 **全局唯一的 Singleton 类对象**。

#### 1. **`s_instance` 是变量，但它的类型是 `Singleton`**

- 从 **变量（Variable）** 的角度看：
  - `s_instance` 是一个静态存储期的变量，存储在程序的全局/静态存储区。
  - 它的生命周期是整个程序运行期间（`main()` 开始前构造，`main()` 结束后析构）。
- 从 **对象（Object）** 的角度看：
  - 由于它的类型是 `Singleton`，所以它也是一个 `Singleton` 类的实例（对象）。
  - 你可以调用它的成员函数，如 `s_instance.print()`。

#### 2. **为什么说它既是变量又是对象？**

- **变量**：它是数据存储的一个命名实体，占用内存空间。
- **对象**：它是某个类的实例，具有成员变量和成员函数。

#### 3. **`static` 关键字的作用**

- 在类内声明 `static Singleton s_instance;` 表示：
  - `s_instance` 是 `Singleton` 类的 **静态成员变量**，不属于任何一个 `Singleton` 对象，而是属于类本身。
  - 所有 `Singleton` 类的实例（如果有的话，尽管单例模式禁止构造其他实例）**共享同一个 `s_instance`**。

#### 4. **单例模式的核心：`s_instance` 是唯一的对象**

- 由于 `Singleton` 的构造函数是 `private`，外部无法创建新的 `Singleton` 对象。

- 因此，`s_instance` 是 **整个程序唯一的 `Singleton` 实例**，通过 `getInstance()` 返回它的引用：

  ```c++
  static Singleton& getInstance() {
      return s_instance; // 返回唯一实例的引用
  }
  ```

#### 5. **对比普通变量 vs. 单例对象**

| 特性                 | 普通全局变量     | `static Singleton s_instance`（单例）   |
| :------------------- | :--------------- | :-------------------------------------- |
| **类型**             | 基本类型或类类型 | 必须是 `Singleton` 类                   |
| **访问控制**         | 无封装，全局可见 | 通过 `getInstance()` 访问，构造函数私有 |
| **生命周期**         | 程序启动到结束   | 程序启动到结束                          |
| **是否允许多个实例** | 可以定义多个     | 只能有一个（单例）                      |

#### 结论：

- **`s_instance` 是一个静态成员变量**（从存储和生命周期角度看）。
- **`s_instance` 也是一个 `Singleton` 类的对象**（从面向对象的角度看）。
- **在单例模式中，它代表全局唯一的实例**，通过 `getInstance()` 提供访问。

### 问题1：为什么 class Singleton 可以包含 static Singleton s_instance 静态成员？

==静态成员的生命周期==：静态成员变量与类本身相关联，而不是与类的任何特定对象相关联（静态成员不属于类）。**静态成员变量的生命周期是整个程序的执行期间**。这意味着静态成员变量**在程序开始运行时 被创建**，并**在程序结束时被销毁**。这个特性使得静态成员变量非常适合用于实现单例模式，因为单**例模式要求有一个全局唯一的对象实例**，该实例在程序的生命周期内一直存在。

 ==初始化时机==：在**类**定义**外**部，我们可以对静态成员变量进行**初始化**。这通常是在类定义之后的某个地方，或者在包含类定义的源文件的顶部。**这个初始化只执行一次，且发生在程序启动时**。因此，对于饿汉式单例模式，我**们在类外部初始化静态成员变量 s_instance ，这样当程序开始运行时，单例对象就已经被创建并准备好了**。 

==访问权限==：**静态成员变量可以通过类名直接访问，而不需要创建类的对象。**这使得静态成员变量成为实现单例模式的理想选择，因为单例模式的设计目标就是允许全局访问唯一的对象实例，而不需要（也不允许）创建该类的多个实例。

### 问题2： class Singleton 可以包含 Singleton s_instance （自身类的对象）非静态成员吗？

不可以，因为 class Singleton 还未创建出来，不确定其大小，但是可以包含 Singleton *s_instance 类型指针变量，因为指针的大小是确定的。

### 问题3：为什么在 Singleton &s1 = Singleton::getInstance(); 要在 s1 前加 &

因为加 & 表示 s1 是这个单例对象的引用，不产生新的对象；而不加 & 表示创建一个新的 s1 对象，用这 个单例对象来初始化，但是构造函数被私有化了，类外无法访问，拷贝构造函数被禁用了。

### 问题4：饿汉式单例模式中，单例对象具体是在什么时候创建的？

在饿汉式单例模式中，**单例对象是在程序启动时创建的**，具体来说，**是在全局静态变量的初始化阶段**。 这个初始化过程发生在程**序的静态存储区分配和初始化阶段**，**通常是在 main 函数执行之前**（新词将该 单例初始化代码放在main函数后也会比main函数先执行）。

 对于饿汉式单例模式，当你定义了一个静态成员变量并给它一个初始值，如 static Singleton s_instance(12345); ，这个变量会在**程序启动时自动被初始化**。这个初始化过程是由编译器在编译时 确定的，不需要任何额外的代码或函数调用。 

下面是一个更详细的解释： 

当编译器遇到类定义中的静态成员变量时，它会记住这个变量需要在程序启动时初始化。 

在链接阶段，编译器和链接器会合作确定所有全局和静态变量的初始化顺序。对于静态成员变量，它们通常按照它们在代码中的声明顺序进行初始化。

当程序开始执行时，在 main 函数之前，全局对象和静态对象（包括静态成员变量）的构造函数会被调用，进行初始化。

对于饿汉式单例模式中的 static Singleton s_instance(12345); ，当程序开始执行时， s_instance 的构造函数会被调用，使用提供的参数 12345 进行初始化。

 一旦 s_instance 被初始化，它就存在于程序的整个生命周期中，可以通过 Singleton::getInstance() 方法安全地访问。

## 饿汉式的优缺点

优点：反应速度快，在程序启动时单例对象就已经创建了，

缺点：由于**饿汉式单例模式的初始化是在程序启动时完成的**，意味着即使单例对象在程序的某些部分中**并未使 用，它仍然会占用内存空间**。 

相比之下，懒汉式单例模式将对象的创建推迟到第一次需要它的时候，这可以节省内存，但**在多线程环境下需要额外的同步机制来确保线程安全。**

## 1.1.2 ==懒汉式==

- 懒汉式单例模式(延时创建);（用时再创建,不用即销毁）
  - 唯一的实例在第一次调用获取实例接口的时候创建,延时初始化
  -  不用到就永远不会创建
  -  避免了饿汉式那种在没有用到的情况下也会创建实例的问题,资源利用率高 
  - 在使用的时候创建,第一次调用的时候反应速度没有饿汉式快

```c++
// 懒汉式
#include<iostream>
using namespace std;
class Singleton
{
private:
int m_data;
    //1)私有化构造函数
    Singleton(int data = 0) :m_data(data)
    {
        cout << "创建单例对象" << endl;
    }
    ~Singleton(void)
    {
        cout << "单例对象被销毁了" << endl;
    }
    // 删除拷贝构造函数
    Singleton(const Singleton&) = delete;

//2)通过静态成员变量维护唯一的对象
static Singleton* s_instance;
//计数,用于记录使用单例对象的人数
static int s_count;

public:
    //单例可以被多个人同时使用,应该是最后有个使用者负责回收
    void release(void)
    {
        if (--s_count == 0)
        {
            delete s_instance;
            s_instance = NULL;
        }
    }
    void print(void)
    {
        cout << m_data << endl;
    }
//3)通过静态成员函数获取单例对象
    static Singleton& getInstance(void)
    {
        if (s_instance == NULL)
        {
            s_instance = new Singleton(54321);
        }
        ++s_count;
        return *s_instance;
    }
};

Singleton* Singleton::s_instance(NULL);
int Singleton::s_count = 0;

int main()
{
    // Singleton s1;
    // Singleton *ps = new Signleton();
    cout << "main开始执行" << endl;
    Singleton& s1 = Singleton::getInstance();//1
    Singleton& s2 = Singleton::getInstance();//2
    cout << "s1 = " << &s1 << endl;
    cout << "s2 = " << &s2 << endl;
    s1.print();
    s1.release();
    s2.print();
    s2.release();
    return 0;
}
```

懒汉式：堆区new，需要手动销毁，delete

# 注意事项

### 问题1：为什么这个实例中单例对象要定义为 static Singleton* s_instance; 而不是 static Singleton s_instance;

在懒汉式单例模式的实现中，单例对象通常定义为指向单例类型的静态指针（ static Singleton* s_instance; ），而不是静态对象（ static Singleton s_instance; ），主要有以下几个原因： 

**==延迟初始化==**：懒汉式单例模式的核心思想是将单例对象的创建延迟到第一次真正需要它的时候。如果使用**静态对象**，那么单例对象会在程序启动时就被创建，这违背了懒汉式单例的初衷。而使用**静态指针**， 我们可以控制单例对象的创建时机，确保在第一次调用 **getInstance** 方法时才进行创建。 

**==动态内存分配==**：使用指针允许我们动态地分配内存给单例对象。这意味着我们可以利用 new 操作符在堆 上创建单例对象，并通过指针来管理它。这种方式提供了更大的灵活性，特别是在处理大型对象或需要更多控制对象生命周期的情况下。

 **==易于销毁==**：通过指针，我们可以更容易地销毁单例对象。当不再需要单例对象时，我们可以使用 delete 操作符释放其占用的内存。如果使用静态对象，则对象的生命周期将与程序的执行期相同，无 法手动销毁。虽然对于单例模式来说，通常不需要显式销毁单例对象，但在某些特殊情况下（如单元测 试或资源清理），手动销毁可能是有益的。

### 问题2：懒汉式单例对象的创建时机？

在这个例子中， **getInstance() 方法**是获取单例对象的入口。当第一次调用这个方法时，会**检查 instance 是否为 null** 。

如果是 null ，则创建一个新的 Singleton 对象，并将其赋值给 instance 。

之后，每次调用 getInstance() 方法都会直接返回这个已经创建好的对象，而不会再创建新的对象。

## 1.1.3二者区别

1. ==对象创建时机==：

   **懒汉式单例**：在第一次使用时才创建对象实例。也就是说，当第一次调用获取单例对象的方法时，才会 进行对象的实例化。这种方式可以节省系统资源，因为只有在真正需要该对象时才会进行实例化。 

   **饿汉式单例**：在类加载时就创建对象实例。无论是否使用，单例对象在类被加载时就已经存在。从资源 利用**效率**的角度来看，饿汉式单例稍差于懒汉式，因为无论是否使用，对象都会被创建。但从速度和**反应时间**角度来看，饿汉式单例稍好于懒汉式，因为它避免了首次使用时的同步或条件检查开销。

2. ==资源初始化和性能==：

**懒汉式单例**：在实例化时，必须处理好多线程同时首次引用该类时访问限制的问题，特别是在单例类作 为资源控制器时，资源初始化可能会耗费时间。 

**饿汉式单例**：对象在类加载时就已存在，无需担心多线程访问或资源初始化的问题，因此性能上可能稍 优。

# 关于线程安全问题

在单例模式下，**线程安全的两层含义**：

1. **单例实例的创建过程是线程安全的**（即多个线程同时首次调用获取实例时，不会创建出多个对象）。
2. **单例对象内部状态的访问是线程安全的**（即多个线程同时调用该对象的成员函数修改其数据时，不会产生数据竞争）。

单例模式只负责第一点（保证唯一实例），但第二点需要开发者自己通过互斥锁、原子操作等手段来实现。如果您的单例对象只是只读的（比如仅提供配置信息读取），那么访问本身可能是安全的；但如果对象有可变状态，则需要额外同步。

所以，更准确的说法是：**单例模式保证了实例的唯一性，但多线程环境下对单例对象的并发访问仍需开发者自行确保同步**。

如：单例对象有一个计数count变量，需要保证它（**共享资源**）的线程安全问题。

## `Q`：C++11 后懒汉模式和饿汉模式都是线程安全的吗？

### 饿汉式

**是线程安全的**。

- 饿汉式的实例在程序启动时（`main` 函数执行之前）通过静态初始化完成。
- 这个阶段是单线程的，且 C++ 保证静态初始化是线程安全的（所有静态对象的初始化在进入 `main` 之前完成，不会有多线程竞争）。
- 因此，后续任何线程调用 `getInstance()` 都只是返回已有实例的引用，不存在创建竞争。

### 懒汉式

**不一定**，取决于具体实现。

#### 经典懒汉式（如上述代码）

```c++
static Singleton& getInstance() {
    if (s_instance == NULL) {
        s_instance = new Singleton(54321);   // 可能被多个线程同时执行！
    }
    ++s_count;
    return *s_instance;
}
```

- 这种写法**不是线程安全**的：多个线程可能同时进入 `if` 语句，导致多次 `new`，从而创建多个对象，违背单例原则。
- 要使其线程安全，需要加锁（例如 `std::mutex`）或使用原子操作 + 双重检查锁定（但双重检查锁定在 C++11 之前有内存序问题，C++11 后可以用原子操作正确实现，但仍较复杂）。

**（带计数的版本）**

- 即使加上锁保护 `new` 的过程，`s_count` 的增减也可能需要原子操作或锁保护，否则 `++s_count` 不是原子操作，仍可能产生计数错误。
- 另外，手动 `delete` 对象并依赖计数释放，在多线程环境下需要非常小心，容易引发 use-after-free 等问题。通常不建议在单例中引入引用计数和手动释放，因为单例的生命周期通常与程序相同。

#### C++11 推荐的线程安全懒汉式：Meyers' Singleton

关于`Meyers' Singleton`：

https://zhuanlan.zhihu.com/p/1889670511144970104

```c++
static Singleton& getInstance() {
    static Singleton instance;   // 函数内的静态局部变量
    return instance;
}
```

- C++11 及以后标准保证：**函数内静态局部变量的初始化是线程安全的**。编译器会自动插入双重检查或互斥机制，确保只初始化一次。
- 这种方式简洁且高效，是懒汉式的最佳实践。

### 总结

- C++11 后：
  - **饿汉式**天然线程安全。
  - **懒汉式**：若采用 Meyers' Singleton（函数局部静态变量），则线程安全；若采用手动 `new` 的经典写法，则需要额外同步。

# 3.1 原子操作详解

原子操作（Atomic Operation）是指**不可被中断**的操作，即要么全部执行完成，要么完全不执行，不会出现执行到一半被其他线程看到的状态。在多线程编程中，原子操作用于实现无锁（lock-free）的线程安全，避免数据竞争（data race）。

------

## 1. C++ 中的原子类型

C++11 开始提供了 `<atomic>` 头文件，定义了模板类 `std::atomic<T>`，可以对任意类型 `T` 进行原子操作。对于内置类型（如 `bool`、`int`、`指针`等），还有专门的别名，例如：

- `std::atomic_bool` → `std::atomic<bool>`
- `std::atomic_int` → `std::atomic<int>`
- `std::atomic<void*>` → `std::atomic<void*>`

常用操作包括：**读（load）**、**写（store）**、**交换（exchange）**、**比较并交换（compare_exchange）** 以及**算术/位运算**（如 `fetch_add`、`fetch_or` 等）。

------

## 2. 核心原子操作方法

假设我们有一个 `std::atomic<int> counter{0};`。

### 2.1 加载与存储

- **`load()`**：原子地读取当前值。

  ```c++
  int val = counter.load();  // 相当于读操作
  ```

- **`store(val)`**：原子地将值写入。

  ```c++
  counter.store(10);         // 相当于写操作
  ```

这两个函数可以接受一个内存序参数（稍后讲解）。

### 2.2 交换

- **`exchange(val)`**：原子地将当前值替换为 `val`，并返回**旧值**。

  ```c++
  int old = counter.exchange(20);  // old 是原来的值，counter 变为 20
  ```

### 2.3 比较并交换（CAS）

这是实现无锁数据结构的关键操作。它比较当前值与预期值，如果相等则更新为目标值，并返回 `true`；否则返回 `false`，并将当前值加载到预期值中。

有两种形式：

- **`compare_exchange_weak(expected, desired)`**：弱版本，可能在符合条件时仍然失败（伪失败），通常用于循环中。
- **`compare_exchange_strong(expected, desired)`**：强版本，保证在相等时一定成功（不会伪失败）。

参数 `expected` 是**引用**类型，既作为输入（期望的值），也作为输出（如果失败，会被更新为当前实际值）。

示例：

```c++
int expected = 10;
int desired = 20;
bool success = counter.compare_exchange_strong(expected, desired);
if (success) {
    // counter 原来是 10，现在被改为 20
} else {
    // counter 不是 10，此时 expected 被更新为 counter 的当前值
}
```

通常用于实现无锁的“检测并更新”逻辑，例如单例的延迟初始化：

```c++
std::atomic<Singleton*> instance{nullptr};
Singleton* tmp = instance.load();
if (tmp == nullptr) {
    Singleton* newInst = new Singleton(...);
    if (instance.compare_exchange_strong(tmp, newInst)) {
        // 成功，newInst 成为全局实例
    } else {
        // 其他线程已经创建了实例，释放 newInst 并复用已有实例
        delete newInst;
    }
}
```

### 2.4 算术与位操作（仅适用于整数类型）

- **`fetch_add(val)`**：原子地将当前值加上 `val`，返回**旧值**。
- **`fetch_sub(val)`**：原子地减去 `val`，返回旧值。
- **`fetch_and(val)`**、**`fetch_or(val)`**、**`fetch_xor(val)`** 等类似。

此外，还有对应的复合赋值运算符重载（如 `+=`、`-=`），但它们返回的是**新值**而不是旧值。

示例：

```c++
int old = counter.fetch_add(5);  // old 是旧值，counter 变为 旧+5
counter += 3;                    // 等价于 fetch_add(3)，但不返回旧值
```

这些操作通常用于计数器、引用计数等场景。

------

## 3. 内存序（Memory Order）

原子操作还允许指定**内存序**参数，控制不同线程间对内存访问的可见性顺序。C++ 定义了六种内存序，常用的有：

| 内存序                 | 含义                                                         |
| :--------------------- | :----------------------------------------------------------- |
| `memory_order_relaxed` | 只保证操作本身原子，不提供任何同步或顺序保证。               |
| `memory_order_consume` | （已弃用）目前不建议使用，基本等同于 `relaxed`。             |
| `memory_order_acquire` | 用于读操作，保证之后的所有读写操作不会被重排到该操作之前。   |
| `memory_order_release` | 用于写操作，保证之前的所有读写操作不会被重排到该操作之后。   |
| `memory_order_acq_rel` | 读-修改-写操作同时具有 acquire 和 release 语义。             |
| `memory_order_seq_cst` | 顺序一致性，最严格，保证所有线程看到完全一致的顺序。默认就是这个。 |

- **acquire/release 配对**：一个线程用 `release` 写入，另一个线程用 `acquire` 读取，可以确保写入之前的所有操作对读取线程可见（类似锁的同步）。
- **`seq_cst`** 提供了全局顺序，但开销最大。

例如，在双重检查锁定中，需要确保对象的构造在指针赋值之前完成，并且其他线程能看到正确的顺序：

```c++
std::atomic<Singleton*> instance{nullptr};

Singleton* getInstance() {
    Singleton* tmp = instance.load(std::memory_order_acquire);
    if (tmp == nullptr) {
        std::lock_guard<std::mutex> lock(mutex);
        tmp = instance.load(std::memory_order_relaxed);
        if (tmp == nullptr) {
            tmp = new Singleton(...);
            instance.store(tmp, std::memory_order_release);
        }
    }
    return tmp;
}
```

- 第一次加载使用 `acquire`：确保一旦看到非空指针，就能看到之前线程在 `release` 之前所做的所有操作（即构造完成）。
- 存储使用 `release`：确保构造过程在指针发布之前对其他线程可见。

------

## 4. 在单例模式中的应用

以引用计数的懒汉式单例为例，使用原子操作可以避免显式锁：

- 使用`std::lock_guard<std::mutex>`锁,格式如下

```c++
static std::mutex s_mutex;
//格式：std::lock_guard<std::mutex> 局部变量名(静态成员互斥锁名)
std::lock_guard<std::mutex> lock(s_mutex); 
//类型：lock的类型为 std::lock_guard<std::mutex>；s_mutex的类型为std::mutex
```

- `s_mutex` 是**真正的互斥锁对象**，负责提供线程间的互斥能力。它是一个静态成员变量，需要在类外定义，并供所有线程共享。
- 而 `lock` 是一个**局部对象**，类型为 `std::lock_guard<std::mutex>`。它的作用是**管理 `s_mutex` 的生命周期**——在构造时自动调用 `s_mutex.lock()` 加锁，在析构时自动调用 `s_mutex.unlock()` 解锁。这是一种 **RAII（资源获取即初始化）** 技术，确保无论代码块是正常退出还是抛出异常，互斥锁都能被正确释放，避免死锁。

```c++
#include <atomic>
#include <iostream>
#include <mutex>

class Singleton {
public:
    static Singleton& getInstance() {
        // 先尝试加载指针(使用 acquire 语义保证看到 release 之前的所有操作)
        Singleton* tmp = s_instance.load(std::memory_order_acquire);
        
        if (tmp == nullptr) {
            //在里面再进行一次if判断，因为防止在 第一个if 之后，执行加锁之前，可能有别的进程已经创建了这个唯一实例；或者这个进程已经创建了这个唯一实例，但是别的进程判断的时候还没有这个实例即仍然是nullptr(在当前进程获得锁来创建实例对象之前，别的进程已经加进入if判断没有实例对象 了。)。
            // 可能首次创建，需要互斥,防止在第一次检查后其他线程已经创建了实例
            std::lock_guard<std::mutex> lock(s_mutex);  // 进入 if 块时加锁
            tmp = s_instance.load(std::memory_order_relaxed);
            if (tmp == nullptr) {
                tmp = new Singleton(54321);
                // 使用 release 语义发布指针，确保构造完成后再被其他线程看到
                s_instance.store(tmp, std::memory_order_release);
            }
        } // 离开 if 块时，lock 对象被销毁，自动解锁
        
        // 原子递增引用计数（relaxed 即可，因为不依赖其他同步）
        s_count.fetch_add(1, std::memory_order_relaxed); // 原子递增
        return *tmp;
    }

    void release() {
        // 原子递减计数，并返回旧值
        if (s_count.fetch_sub(1, std::memory_order_relaxed) == 1) {
            // 最后一个使用者，需要加锁安全销毁
            std::lock_guard<std::mutex> lock(s_mutex); // 进入 if 块时加锁
            delete s_instance.load();
            s_instance.store(nullptr, std::memory_order_relaxed);
        }
    } // 离开 if 块时，lock 对象被销毁，自动解锁

    
    void print() const {
        std::cout << m_data << std::endl;
    }
    
private:
    Singleton(int data = 0) : m_data(data) {
        std::cout << "创建单例对象" << std::endl;
    }
    ~Singleton() {
        std::cout << "单例对象被销毁了" << std::endl;
    }
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;

    int m_data;
    static std::atomic<Singleton*> s_instance;
    static std::atomic<int> s_count;
    static std::mutex s_mutex;
};

// 静态成员定义
std::atomic<Singleton*> Singleton::s_instance{nullptr};
std::atomic<int> Singleton::s_count{0};
std::mutex Singleton::s_mutex;
int main() {
    std::cout << "main 开始执行" << std::endl;

    Singleton& s1 = Singleton::getInstance();
    Singleton& s2 = Singleton::getInstance();

    std::cout << "s1 地址 = " << &s1 << std::endl;
    std::cout << "s2 地址 = " << &s2 << std::endl;

    s1.print();
    s2.print();

    s1.release();  // 第一个使用者释放，计数从 2 -> 1，对象仍存活
    s2.release();  // 第二个使用者释放，计数从 1 -> 0，对象被销毁

    std::cout << "main 结束" << std::endl;
    return 0;
}
```

- 使用 `fetch_add` / `fetch_sub` 原子地修改引用计数，无锁高效。
- 在 `getInstance` 中，首次创建用 `mutex` 保护，但只发生在第一次，后续直接原子加载。
- 内存序保证了正确的可见性（确保对象构造完全后才被其他线程看到）。
- `std::lock_guard<std::mutex> lock(s_mutex);` 是一个**RAII（资源获取即初始化）** 风格的锁管理对象。它的工作原理如下：
  - **构造时**：`lock` 对象被创建，其构造函数会自动调用 `s_mutex.lock()`，对互斥量加锁。
  - **析构时**：当 `lock` 对象离开其作用域时（即所在的代码块结束时），其析构函数会自动调用 `s_mutex.unlock()`，释放互斥锁。

## 5. 注意事项

- **ABA 问题**：CAS 操作可能遇到变量值从 A 变成 B 再变回 A，此时 CAS 会成功，但可能不符合逻辑（例如链表节点复用）。一般需要配合版本号或使用 `std::atomic<std::shared_ptr>` 等方式解决。
- **伪失败**：`compare_exchange_weak` 可能在条件满足时仍返回 `false`，通常用于循环中，需要重试；而 `compare_exchange_strong` 不会伪失败，但性能略低。
- **内存序选择**：默认 `seq_cst` 最容易理解，但开销大；理解项目需求后可使用较弱的序提升性能。
- **非平凡类型**：`std::atomic<T>` 要求 `T` 是**可平凡复制**的（trivially copyable），否则可能无法使用原子操作（通常需要锁来实现）。

# 4.1 使用静态局部变量

在 C++11 及以后的版本中，可以利用**函数内的静态局部变量**来实现线程安全的懒汉式单例，这种方式被称为 **Meyers' Singleton**。它既简洁又高效，无需显式加锁或使用原子操作，因为 C++ 标准保证了静态局部变量初始化的线程安全性。

**在全局数据区，即堆区，只要数据的默认值为0则认为是未初始化。**

**在C++11标准中有以下规定，并且这个操作是在编译时由编译器保证的：**

- ==**如果指令逻辑进入一个未被初始化的声明变量，所有并发执行应该等待该变量完成初始化。**==

这意味着：

- 当多个线程第一次调用 `getInstance()` 并试图初始化 `static Singleton instance` 时，只有一个线程会执行构造函数，其他线程会阻塞直到初始化完成。
- 初始化完成后，所有后续调用直接返回已构造好的对象，无需任何同步开销。

```c++
class Singleton {
public:
    // 禁止拷贝和赋值
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;

    // 全局访问点
    static Singleton& getInstance() {
        static Singleton instance;   // 静态局部变量
        return instance;
    }

    void doSomething() {
        // 业务逻辑
    }

private:
    // 私有构造函数和析构函数
    Singleton() {
        // 初始化代码
    }
    ~Singleton() = default;
};
```

**使用方法**：

```c++
Singleton& s1 = Singleton::getInstance();
Singleton& s2 = Singleton::getInstance();
// s1 和 s2 指向同一个对象
```

**优点**：

- **线程安全**：由标准保证，无需手动加锁。
- **性能优异**：初始化后无锁竞争，调用开销极低（相当于普通函数调用）。
- **代码简洁**：无需管理互斥锁、原子变量或引用计数。
- **自动析构**：静态局部变量在程序结束时自动销毁，析构函数会被调用，无需手动释放。

# 在实际开发中：

- 如果对初始化时机无特殊要求，使用**饿汉式**最简单安全。
- 如果需要**懒加载**，优先使用 Meyers' Singleton（C++11 后）。
  - **利用局部变量（函数内静态）解决单例线程安全问题**是 C++ 中最推荐的做法，除非有特殊需求（如跨 DLL、需要手动销毁）。它充分利用了语言标准提供的线程安全保证，让代码更简洁、健壮且高效。

- 若必须手动管理生命周期（如需要提前销毁），则需谨慎设计同步机制，并优先使用现代 C++ 的原子操作和锁。
